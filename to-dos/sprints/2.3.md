## Acceptance and stopping point

Navigation and cancellation never authenticate by themselves. Copy prints no OTP;
show displays only validated codes until dismissal. Codes and item inventories
never persist. Explicitly configured account/vault IDs and local store paths may
persist in the private resident TUI profile, together with an optional 1Password
metadata tag filter.
Tiny terminals, resize, missing curses and interruption produce safe outcomes.
Installation preview cannot apply changes; migration screens never operate accounts
or turn checklist navigation into verified migration evidence.

Run the aggregate gate and isolated package smoke. Human synthetic acceptance must
cover the installed TUI before real migration. Mark completion only from evidence.
Scratch files belong under `/tmp/Authy-to-1Password_Local/`; no commits or publication.

## Resident scope and native browsing refinement

The operator requested resident 1Password scope and direct browsing of 1Password
and local-store items. This extends T-AUTH-059 and T-AUTH-061; it introduces no new
phase or task IDs. Implementation and verification remain tracked in
[project status](../../PROJECT-STATUS.md).

Acceptance for this refinement requires:

- Configure backend scope through key 8 or p and restore it across TUI launches.
- Save only validated account/vault IDs and store/configuration paths in an owned
  0600 profile under a 0700 directory; reject unsafe or malformed profiles.
- Open scoped metadata with keys 4/5 in a native searchable curses browser;
  refresh only on explicit request and retrieve only the selected item's code.
- Preserve actions 2/3 for manual item entry with resident scope, backend choice
  through b, hidden scope input and safe cancellation/terminal restoration.
- Keep CLI scope explicit, metadata transient and enrollment outside the TUI;
  package the matching public guide and run synthetic and installed acceptance.

## Local deletion refinement

The operator explicitly requested deletion from local-store browsers. This
extends T-AUTH-059 and T-AUTH-061 and supersedes the former read-only TUI boundary
only for confirmed single-entry pass-otp/GPG and totpm/TPM deletion.

Acceptance requires a named confirmation through d, visible `DELETE` plus Enter,
and default cancellation on Escape, resize or interruption. GPG deletion targets
one validated flat private ciphertext; TPM-backed deletion transactionally removes
one exact service/account database row in the pinned local-mode schema. Reject
unknown schema, triggers, views, unsupported presence modes and unsafe paths.
No decrypted seed reads, native TPM operations, key removal, store initialization, TPM clearing/eviction,
1Password deletion, bulk deletion or service-factor changes are permitted.

The coarse private audit must be written before deletion and audit failure must
block it. No identifying labels, IDs, paths, seeds or codes enter the audit.
Refresh after success and discard stale metadata if listing fails. Synthetic
regressions and installed acceptance must cover these safeguards. Backups and
copied seeds are unaffected; secure erasure is not claimed. Enrollment remains
an explicit CLI/operator workflow outside the TUI.

## Doctor status and tag-filter refinement

The operator requested a retained Session Status result and tagged current
1Password OTP items with `OTP`. This extends T-AUTH-059 and T-AUTH-061.

Acceptance requires:

- Retain the latest explicit Doctor capability summary across dashboard redraws
  for this TUI session; keep authentication unknown and perform no background check.
- Save an optional single metadata tag with the 1Password scope, defaulting to
  `OTP` for both new scopes and legacy account/vault-only profiles.
- Edit the tag through key 8 or p; Ctrl-U and blank submission disable filtering.
- Apply a nonempty filter through `op item list --tags` only; accept the vendor's
  nested-tag matching, retain Login/category/account/vault scope and bounded metadata.
- Keep tags operator-maintained: no guarantee of an OTP field and no bulk field,
  seed or code reads. Keep CLI `select` independent of TUI profiles.
- Verify synthetic status retention, profile compatibility and filtered listing;
  bundle the updated guide and verify the installed candidate with synthetic data.

Implementation and verification are tracked in [project status](../../PROJECT-STATUS.md).
