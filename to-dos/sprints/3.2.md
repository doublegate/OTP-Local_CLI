# S-AUTH-3.2: Staged migration and exceptions

Status: planned. Task IDs are allocated in [ROADMAP.md](../../ROADMAP.md).

## Goal and scope

Complete supported accounts in small recoverable batches and classify every exception.

Non-goals: No bulk export, unattended MFA changes, deletion based on aggregate counts, or forced proprietary-token conversion.

## Entry conditions and dependencies

Dependencies: S-AUTH-3.1; explicit authorization for each batch scope.
Read the [specification](../../docs/specs/07-migration-and-recovery.md) and current [project status](../../PROJECT-STATUS.md).
Any required operator authorization must name the concrete action and scope before execution.

## Tasks

- [ ] **T-AUTH-038:** Human classifies private inventory into standard TOTP, hardware-key preference, proprietary Authy integration, and blocked recovery cases.
- [ ] **T-AUTH-039:** Execute separately scoped batches from low to high impact; verify independent recovery, enrollment, and fresh login for every account.
- [ ] **T-AUTH-040:** Handle proprietary services through their current supported alternative MFA or recovery flow; retain Authy mobile when no safe migration exists.
- [ ] **T-AUTH-041:** Reconcile aggregate planned/migrated/blocked/retained counts and private evidence after each batch; update status without account identities.

## Outputs

Account coverage reconciliation, private per-account evidence, and aggregate exception disposition.

Store operational identities and per-account evidence in the private external ledger.
Only aggregate outcomes and non-secret validation reports belong in the repository.

## Validation and TDD

Each migrated account requires its own fresh-login pass. A count mismatch, failed login, or missing recovery blocks the batch; successful code generation alone never marks migration complete.
For implementation tasks, retain the failing regression as evidence, then record the passing gate.
For operator tasks, use human attestations and service login results; automated mocks cannot prove live readiness.

## Risks and blockers

High-impact accounts require more elapsed operator coordination; proprietary integrations may prevent full Authy retirement.

## Exit and stop gate

Pause at the first failed access/recovery check. Do not advance to higher-risk batches or claim zero Authy dependency while exceptions remain.
Update PROJECT-STATUS.md only from observed evidence; leave unchecked work planned.
Use a scratch directory under /tmp/Authy-to-1Password_Local/ for volatile sprint notes.

## Effort

Estimated active effort: Variable: 15–45 minutes per ordinary account. This is not a deadline.
Operator availability, service recovery, approval prompts, and waiting periods add elapsed time.
